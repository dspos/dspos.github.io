5 年经验 Java 后端开发 - Java SE 核心面试宝典

你是一位拥有 15 年经验的互联网大厂 Java 技术专家/架构师，曾担任过多次 P7/P8 级别的技术面试官。你深知对于 5 年经验的候选人，考察重点不再是 API 的用法，而是底层原理、源码理解、性能调优及复杂场景下的解决方案。

核心考察范围

严格围绕以下高难度领域出题，避开基础语法和简单概念：

  1. JVM 深度调优：内存模型 (JMM)、垃圾回收器 (G1/ZGC) 原理与选型、OOM 排查实战、类加载机制与热部署、字节码增强

题目 1：请手写或口述 AQS 的 tryAcquire 流程

【题目描述】
你在项目中大量使用了 ReentrantLock、CountDownLatch 等基于 AQS 的并发工具。现在我想知道，你是否真正理解 AQS 的底层原理？请详细描述 tryAcquire 的完整流程，最好能结合源码。

【考察意图】

  • 是否真正读过 AQS 源码，而非仅仅停留在使用层面
  • 对 CAS、volatile 等并发原语的理解深度
  • 是否理解独占锁与共享锁的区别
  • 考察候选人是否具备阅读 JDK 源码的习惯和能力

【参考回答要点】

  1. AQS 核心结构：

    • state 变量（volatile int）表示同步状态
    • CLH 双向队列管理等待线程
    • 线程通过 CAS 尝试修改 state

  2. tryAcquire 流程（以 ReentrantLock 为例）：

  1. 关键关键词：

    • CAS (Compare-And-Swap) 保证原子性
    • volatile 保证可见性
    • 公平锁 vs 非公平锁的区别
    • 可重入机制（通过记录持有锁的线程）

  2. 失败后的处理：

    • tryAcquire 失败后，线程会被封装成 Node 加入 CLH 队列
    • LockSupport.park() 挂起线程
    • 等待前驱节点释放锁后唤醒

【加分项/杀手锏】

  • 对比 Java 21 虚拟线程：传统平台线程使用 AQS 时会阻塞操作系统线程，而虚拟线程在 park 时会卸载到载体线程，大幅提升吞吐量
  • AQS 的变体：提到 LongAddable 在高并发场景下比 AQS 更优（分段 CAS 减少竞争）
  • 源码细节：提到 hasQueuedPredecessors() 是公平锁的关键，非公平锁会跳过这个检查直接 CAS

题目 2：ConcurrentHashMap 在 JDK 1.8 中的底层实现细节，与 1.7 有何本质区别？

【题目描述】
ConcurrentHashMap 是高并发场景下的必备工具。我想知道你是否真正理解它在 JDK 1.8 中的重构，以及为什么要做这些改动？

【考察意图】

  • 对并发容器演进的理解
  • 是否理解锁粒度优化（Segment -> CAS+synchronized）
  • 对红黑树优化场景的认知
  • 考察候选人是否关注技术演进背后的设计思想

【参考回答要点】

  1. JDK 1.7 vs 1.8 核心区别：

    维度 JDK 1.7 JDK 1.8
    数据结构 数组 + 链表 + Segment 数组 + 链表/红黑树
    锁机制 Segment 分段锁 CAS + synchronized
    锁粒度 段级别 桶（Node）级别
    并发度 取决于 Segment 数量 更高，桶级别并发

  2. JDK 1.8 核心优化：

    • 废弃 Segment：改用 Node 数组，每个桶是一个链表/红黑树
    • CAS + synchronized：
      • 插入节点时使用 CAS 尝试
      • 冲突时使用 synchronized 锁住桶首节点
    • 红黑树优化：
      • 链表长度 > 8 且数组长度 > 64 时转为红黑树
      • 查找复杂度从 O(n) 降到 O(log n)

  3. 扩容机制：

    • 多线程协同扩容（Transfer 任务）
    • 支持并发迁移数据
    • 使用 ForwardingNode 标记已迁移的桶

  4. size 统计：

    • 使用 LongAdder 类似的分段累加机制
    • 避免全局锁竞争

【加分项/杀手锏】

  • 性能对比数据：在高并发场景下，JDK 1.8 的 ConcurrentHashMap 吞吐量是 1.7 的 3-5 倍
  • 红黑树退化：提到当节点数 < 6 时红黑树会退化为链表
  • 实际踩坑经验：分享在极端场景下（大量 hash 冲突）红黑树退化的案例
  • 与 HashMap 对比：提到 HashMap 在 1.8 也引入了红黑树，但不支持并发

题目 4：请解释 G1 垃圾回收器的工作原理，以及它相比 CMS 的优势

【题目描述】
G1 是 Java 9 的默认垃圾回收器，现在生产环境也广泛使用。我想知道你是否真正理解 G1 的设计哲学，以及如何在实际场景中进行调优？

【考察意图】

  • 对现代垃圾回收器的理解深度
  • 是否有线上 GC 调优经验
  • 是否能根据业务场景选择合适的回收器
  • 考察候选人是否理解 GC 性能指标（停顿时间、吞吐量）

【参考回答要点】

  1. G1 核心设计：

    • Region 分区：将堆内存划分为多个 Region（默认 2048 个）
    • Region 类型：Eden、Survivor、Old、Humongous（大对象）
    • 可预测停顿模型：用户指定最大停顿时间（-XX:MaxGCPauseMillis）

  2. 回收流程：

    • Young GC：回收 Eden 区，存活对象复制到 Survivor 或 Old 区
    • Mixed GC：回收部分 Old 区（基于回收价值排序）
    • Full GC：单线程回收整个堆（应避免）

  3. G1 vs CMS：

    维度 CMS G1
    算法 Mark-Sweep Mark-Compact
    停顿时间 不可预测 可预测
    内存碎片 有 无（整理）
    大堆支持 一般 优秀（>6G）

  4. 关键参数：

  5. 调优经验：

    • 避免 Humongous 对象（超过 Region 50% 的对象）
    • 监控 Full GC 频率（说明堆太小或停顿时间太激进）
    • 使用 GC 日志分析工具（GCViewer、GCEasy）

【加分项/杀手锏】

  • ZGC 对比：提到 ZGC 在 Java 15+ 成为生产级，停顿时间 < 10ms，适合超低延迟场景
  • 实际调优案例：分享通过调整 MaxGCPauseMillis 和 IHOP 参数将 GC 停顿从 500ms 降到 100ms 的经验
  • GC 日志分析：能读懂 G1 GC 日志中的 Evacuation Failure、To-Region 等关键信息
  • Java 21 新特性：提到 Generational ZGC（分代 ZGC）在 Java 21 成为生产级

题目 10：Java 21 虚拟线程 (Project Loom) 原理与应用场景

【题目描述】
Java 21 是 LTS 版本，虚拟线程是最大亮点。我想知道你是否理解虚拟线程的原理，以及它在什么场景下能发挥最大价值？

【考察意图】

  • 是否持续学习新技术
  • 对并发模型演进的理解
  • 是否能将新技术与实际业务结合
  • 考察候选人的技术敏感度和学习能力

【参考回答要点】

  1. 虚拟线程 vs 平台线程：

    维度 平台线程 虚拟线程
    映射 1:1 映射到 OS 线程 M:N 映射到 OS 线程
    内存占用 ~1MB 栈空间 ~1KB 初始栈
    创建成本 高（系统调用） 低（JVM 管理）
    阻塞行为 阻塞 OS 线程 卸载到载体线程
    适用场景 计算密集型 IO 密集型

  2. 核心原理：

    • 载体线程（Carrier Thread）：平台线程作为载体
    • 挂载/卸载：虚拟线程阻塞时卸载，IO 完成后重新挂载
    • 调度器：JVM 内部的 ForkJoinPool 调度虚拟线程
    • 连续栈：虚拟线程栈可动态扩展，支持栈复制

  3. 使用方式：

  4. 适用场景：

    • 高并发 IO：HTTP 服务器、数据库连接
    • 大量阻塞调用：RPC、文件 IO
    • 不适用：计算密集型任务（CPU 绑定）

  5. 性能提升：

    • 单机支持百万级并发线程
    • 吞吐量提升 5-10 倍
    • 代码风格同步，性能异步

【加分项/杀手锏】

  • 实际压测数据：展示在 Spring Boot 3.2 + Tomcat 10.1 场景下，使用虚拟线程后 QPS 从 5000 提升到 50000
  • 平台线程池陷阱：提到虚拟线程不应使用有界线程池，会导致载体线程耗尽
  • Pinning 问题：提到在 synchronized 块或 native 方法中虚拟线程无法卸载
  • 生态兼容：提到主流框架（Spring Boot、Quarkus）已支持虚拟线程，但部分库（如 HikariCP）需要适配

总结

这份面试宝典涵盖了 5 年经验 Java 后端开发工程师应该掌握的核心知识点：

  1. 深度原理：AQS、ConcurrentHashMap、类加载、G1 GC
  2. 场景设计：CPU 排查、无锁计数器、异步编排、限流系统
  3. 陷阱调优：ThreadLocal 内存泄漏、虚拟线程实战

给候选人的建议：

  • 不要死记硬背，理解背后的设计思想
  • 多读源码，培养代码敏感度
  • 积累线上排查经验，建立方法论
  • 关注技术演进，保持学习热情

给面试官的建议：

  • 根据候选人回答深度灵活调整问题
  • 关注思考过程而非标准答案
  • 结合实际场景考察解决问题的能力
  • 给予候选人提问和深入探讨的机会

祝各位候选人面试顺利，拿到心仪的 Offer！
