JVM内存模型深度解析

运行时数据区架构、内存屏障与原子操作

主内存与工作内存机制

JVM内存模型定义了程序如何使用计算机内存资源。核心包括主内存（所有线程共享，存储所有变量实例）和工作内存（每个线程私有，缓存变量副本）。
通过内存屏障或同步操作实现主内存和工作内存的数据一致性。

JMM的8种原子操作

JMM定义了8种原子操作保证内存可见性和有序性：

  • lock/unlock
  • read/load
  • use/assign
  • store/write

线程解锁前必须将共享变量立即刷新回主存，加锁前必须读取主存最新值。

JVM运行时数据区架构

垃圾回收机制与调优实战

GC算法、回收器家族与性能调优方法论

可达性分析

从GC Roots（虚拟机栈局部变量、方法区静态属性等）开始向下搜索，形成引用链。对象到GC Roots无引用链相连时，判定为不可用。

复制算法

将内存分为两部分，存活对象复制到另一区域。存活对象较少时效率高，适用于年轻代（Eden区和两个Survivor区8:1:1比例）。

标记-整理

标记需回收对象，将存活对象移动到一端。减少内存碎片，适用于老年代Full GC。

垃圾回收器家族演进
收集器 特点 适用场景
Serial/Serial Old 单线程收集器，垃圾收集时暂停所有用户线程 基本不再使用
CMS 以最短回收停顿时间为目标，并发收集器，Mark-Sweep算法 老年代收集，响应时间敏感
G1 (Garbage-First) 堆内存分为2048个小块，建立可预测停顿时间模型，Java9默认回收器 服务端应用，大内存堆
GC调优核心原则

根本原则：每次GC都回收尽可能多的对象，减少无用功。

  • 吞吐量：执行用户代码时间 / (执行用户代码时间 + GC时间)
  • 延迟：GC延迟 + 业务执行时间
  • 内存使用量：Java应用占用系统内存的最大值，应尽可能小

类加载机制与双亲委派模型

四层加载器架构、委派流程与打破双亲委派的场景

Java类加载器层次结构
  • 启动类加载器：加载JAVA_HOME/lib核心类库（rt.jar），C++实现，无父加载器
  • 扩展类加载器：加载JAVA_HOME/lib/ext目录类库，父加载器是启动类加载器
  • 应用程序类加载器：加载用户类路径（ClassPath）下的类，父加载器是扩展类加载器
双亲委派模型核心思想

“当一个类加载器需要加载某个类时，它首先不会自己尝试加载，而是委托给父加载器；只有当父加载器无法加载时，才会自己尝试加载。”

JUC多线程并发编程

线程池参数配置与拒绝策略、锁机制与锁升级过程、AQS原理、CAS及volatile关键字

线程池参数配置与拒绝策略

线程池核心参数：

  • corePoolSize：核心线程数，线程池维护的最小线程数
  • maximumPoolSize：最大线程数，线程池允许的最大线程数
  • keepAliveTime：非核心线程的存活时间
  • workQueue：工作队列，存储等待执行的任务
  • threadFactory：线程工厂，创建新线程的工厂
  • handler：拒绝策略，当线程池和队列都满时的处理策略

线程池拒绝策略：

  • AbortPolicy：直接抛出异常（默认）
  • CallerRunsPolicy：由调用线程执行任务
  • DiscardPolicy：直接丢弃任务
  • DiscardOldestPolicy：丢弃队列中最旧的任务
锁机制与锁升级过程

锁的分类：

  • 偏向锁：适用于单线程访问的场景，减少锁开销
  • 轻量级锁：适用于多线程交替访问的场景
  • 重量级锁：适用于多线程竞争激烈的场景

锁升级过程：

  1. 无锁状态
  2. 偏向锁（单线程访问）
  3. 轻量级锁（多线程交替访问）
  4. 重量级锁（多线程竞争激烈）
AQS原理

AbstractQueuedSynchronizer（AQS）是Java并发包的基础框架，用于构建锁和同步器。核心原理：

  • 状态管理：使用volatile修饰的state变量管理同步状态
  • 双向链表：维护等待线程的双向链表
  • CAS操作：使用CAS原子操作修改状态
  • 条件变量：提供Condition接口实现线程等待/唤醒
CAS及volatile关键字

CAS（Compare-And-Swap）：

  • 原子操作，比较并交换
  • 三个参数：内存地址、预期值、新值
  • 只有当内存地址的值等于预期值时，才将新值写入内存

volatile关键字：

  • 保证内存可见性：一个线程修改了volatile变量，其他线程能立即看到最新值
  • 禁止指令重排序：确保指令执行顺序与代码顺序一致
  • 不保证原子性：复合操作仍需加锁

Spring源码解析与核心原理

深入理解Spring框架的核心原理，包括IoC容器、AOP实现、Bean生命周期、事务管理等。

IoC容器

IoC（Inversion of Control）：控制反转，将对象的创建和依赖管理交给Spring容器。

BeanFactory vs ApplicationContext：

  • BeanFactory：基础IoC容器，延迟加载
  • ApplicationContext：高级IoC容器，继承BeanFactory，提供更多功能

Bean的作用域：

  • singleton：单例（默认）
  • prototype：原型
  • request：请求作用域
  • session：会话作用域
  • globalSession：全局会话作用域

AOP实现

AOP（Aspect-Oriented Programming）：面向切面编程，将横切关注点从业务逻辑中分离。

核心概念：

  • Aspect：切面
  • Join Point：连接点
  • Pointcut：切入点
  • Advice：通知
  • Target：目标对象
  • Weaving：织入

实现方式：

  • 基于代理：JDK动态代理（接口）、CGLIB代理（类）
  • 基于字节码增强：AspectJ

Bean生命周期

Bean的生命周期：

  1. 实例化：创建Bean实例
  2. 属性赋值：设置Bean的属性
  3. 初始化前：执行BeanPostProcessor的postProcessBeforeInitialization方法
  4. 初始化：执行init-method或InitializingBean接口的afterPropertiesSet方法
  5. 初始化后：执行BeanPostProcessor的postProcessAfterInitialization方法
  6. 使用：Bean可以被使用
  7. 销毁：执行destroy-method或DisposableBean接口的destroy方法

事务管理

事务的ACID特性：

  • Atomicity：原子性
  • Consistency：一致性
  • Isolation：隔离性
  • Durability：持久性

事务隔离级别：

  • READ_UNCOMMITTED：读未提交
  • READ_COMMITTED：读已提交
  • REPEATABLE_READ：可重复读
  • SERIALIZABLE：串行化

事务传播行为：

  • REQUIRED：如果当前存在事务，加入事务；否则创建新事务
  • SUPPORTS：如果当前存在事务，加入事务；否则以非事务方式执行
  • MANDATORY：如果当前存在事务，加入事务；否则抛出异常
  • REQUIRES_NEW：创建新事务，暂停当前事务
  • NOT_SUPPORTED：以非事务方式执行，暂停当前事务
  • NEVER：以非事务方式执行，如果当前存在事务，抛出异常
  • NESTED：如果当前存在事务，创建嵌套事务；否则创建新事务

分布式系统架构

掌握分布式系统的核心概念和设计原则，包括CAP理论、分布式一致性、分布式锁、分布式事务等。

CAP理论

CAP：

  • Consistency：一致性
  • Availability：可用性
  • Partition Tolerance：分区容错性

CAP权衡：

  • CA：放弃分区容错性，适用于单节点系统
  • CP：放弃可用性，适用于对一致性要求高的场景
  • AP：放弃一致性，适用于对可用性要求高的场景

分布式一致性

一致性算法：

  • Paxos：基于提案-投票机制
  • Raft：基于领导者选举
  • ZooKeeper：基于ZAB协议

一致性级别：

  • 强一致性：所有节点数据实时一致
  • 最终一致性：经过一段时间后所有节点数据一致
  • 弱一致性：不保证所有节点数据一致

分布式锁

实现方式：

  • 基于Redis：使用SETNX命令
  • 基于ZooKeeper：使用临时节点
  • 基于数据库：使用唯一索引

分布式锁的特性：

  • 互斥性：同一时间只有一个线程能获取锁
  • 可重入性：同一线程可以多次获取锁
  • 超时机制：避免死锁
  • 高可用性：锁服务不可用时仍能工作

分布式事务

实现方式：

  • 两阶段提交（2PC）：准备阶段和提交阶段
  • 三阶段提交（3PC）：增加了预提交阶段
  • TCC（Try-Confirm-Cancel）：业务层面的两阶段提交
  • 本地消息表：基于消息队列的最终一致性
  • Saga：长事务的补偿机制

高并发场景设计

应对千万级并发挑战，掌握限流、熔断、降级、缓存等核心技术。

限流

限流算法：

  • 计数器法：固定时间窗口内限制请求数
  • 滑动窗口法：滑动时间窗口内限制请求数
  • 令牌桶法：以固定速率生成令牌，请求需要获取令牌才能执行
  • 漏桶法：以固定速率处理请求，超出部分进入桶中等待

限流实现：

  • 基于Redis：使用Redis的incr命令和过期时间
  • 基于Guava：使用RateLimiter
  • 基于Nginx：配置limit_req模块

熔断

熔断机制：

  • 当服务调用失败率超过阈值时，熔断服务调用
  • 熔断后，请求直接返回错误，不调用服务
  • 经过一段时间后，尝试半开状态，允许部分请求通过
  • 如果半开状态下请求成功，关闭熔断；否则继续熔断

熔断实现：

  • Hystrix：Netflix开源的熔断库
  • Sentinel：阿里巴巴开源的熔断库

降级

降级策略：

  • 服务降级：当服务不可用时，返回兜底数据
  • 接口降级：当接口响应慢时，返回缓存数据
  • 页面降级：当页面加载慢时，显示简化版页面

降级实现：

  • 基于配置：通过配置中心动态配置降级策略
  • 基于代码：在代码中添加降级逻辑

缓存

缓存策略：

  • 缓存穿透：查询不存在的数据，使用布隆过滤器
  • 缓存雪崩：缓存同时过期，使用随机过期时间
  • 缓存击穿：热点数据过期，使用互斥锁

缓存实现：

  • 本地缓存：Guava Cache、Caffeine
  • 分布式缓存：Redis、Memcached

数据库优化

深入理解数据库优化策略，包括索引设计、SQL优化、分库分表等。

索引设计

索引类型：

  • 主键索引：唯一标识记录
  • 唯一索引：保证列值唯一
  • 普通索引：加速查询
  • 复合索引：多列组合索引
  • 全文索引：全文搜索

索引优化：

  • 选择高选择性的列作为索引
  • 避免在索引列上使用函数
  • 复合索引遵循最左前缀原则
  • 定期重建索引

SQL优化

SQL优化策略：

  • 避免使用SELECT *
  • 使用EXPLAIN分析执行计划
  • 避免在WHERE子句中使用函数
  • 避免使用OR，使用UNION ALL代替
  • 合理使用JOIN，避免笛卡尔积

执行计划分析：

  • type：访问类型（ALL、index、range、ref、eq_ref、const、system）
  • key：使用的索引
  • rows：扫描的行数
  • Extra：额外信息（Using index、Using filesort、Using temporary）

分库分表

分库分表策略：

  • 水平分库：按业务或数据范围拆分数据库
  • 水平分表：按数据范围或哈希拆分表
  • 垂直分库：按业务拆分数据库
  • 垂直分表：按列拆分表

分库分表中间件：

  • Sharding-JDBC：客户端分片
  • MyCAT：服务端分片
  • DRDS：阿里云分布式数据库服务

微服务架构

掌握微服务架构的设计原则和实践，包括服务注册与发现、服务网关、配置中心等。

服务注册与发现

服务注册：

  • 服务启动时向注册中心注册服务信息
  • 定期发送心跳，保持服务状态

服务发现：

  • 客户端从注册中心获取服务列表
  • 基于负载均衡选择服务实例

注册中心：

  • Eureka：Netflix开源的注册中心
  • Consul：HashiCorp开源的服务网格解决方案
  • ZooKeeper：Apache开源的分布式协调服务
  • Nacos：阿里巴巴开源的服务注册与配置中心

服务网关

服务网关职责：

  • 请求路由：将请求路由到对应的服务
  • 负载均衡：在多个服务实例间分配请求
  • 认证授权：验证请求的身份和权限
  • 限流熔断：保护后端服务
  • 日志监控：记录请求和响应

服务网关实现：

  • Zuul：Netflix开源的服务网关
  • Gateway：Spring Cloud官方的服务网关
  • Kong：基于Nginx的API网关

配置中心

配置中心职责：

  • 集中管理配置
  • 动态更新配置
  • 配置版本管理
  • 配置权限控制

配置中心实现：

  • Config：Spring Cloud官方的配置中心
  • Nacos：阿里巴巴开源的配置中心
  • Apollo：携程开源的配置中心
  • Consul：HashiCorp开源的配置中心
