JVM 内存模型深度解析

主内存与工作内存机制

JVM 内存模型定义了程序如何使用计算机内存资源。核心包括主内存（所有线程共享，存储所有变量实例）和工作内存（每个线程私有，缓存变量副本）。

通过内存屏障或同步操作实现主内存和工作内存的数据一致性。

JMM 的 8 种原子操作

JMM 定义了 8 种原子操作保证内存可见性和有序性：

  • lock/unlock：锁定/解锁主内存变量
  • read/load：读取主内存变量到工作内存
  • use/assign：使用工作内存变量/赋值给工作内存变量
  • store/write：存储工作内存变量到主内存

关键规则：线程解锁前必须将共享变量立即刷新回主存，加锁前必须读取主存最新值。

GC 调优核心原则

根本原则：每次 GC 都回收尽可能多的对象，减少无用功。

  • 吞吐量 = 执行用户代码时间 / (执行用户代码时间 + GC 时间)
  • 延迟 = GC 延迟 + 业务执行时间
  • 内存使用量：Java 应用占用系统内存的最大值，应尽可能小

类加载机制与双亲委派模型

类加载器四层架构

  • 启动类加载器：加载 JAVA_HOME/lib 核心类库（rt.jar），C++实现，无父加载器
  • 扩展类加载器：加载 JAVA_HOME/lib/ext 目录类库，父加载器是启动类加载器
  • 应用程序类加载器：加载用户类路径（ClassPath）下的类，父加载器是扩展类加载器

双亲委派模型核心思想

“当一个类加载器需要加载某个类时，它首先不会自己尝试加载，而是委托给父加载器；只有当父加载器无法加载时，子加载器才会尝试自己加载。”

三大价值：

  1. 安全性：防止核心类被篡改（自定义 java.lang.Object 无效）
  2. 唯一性：避免重复加载导致类冲突
  3. 资源隔离：不同加载器加载的类互不可见，支持模块化

打破双亲委派的典型场景

1. SPI 机制

JDBC 核心接口由启动类加载器加载，具体 Driver 实现由应用程序类加载器加载。使用线程上下文类加载器解决委托问题。

2. Tomcat 类隔离

同时部署多个 Web 应用可能依赖不同版本类。自定义 WebAppClassLoader，优先加载当前 Web 应用类，再委托父加载器。

3. OSGi 模块化

支持模块热部署，依赖关系复杂。需要更灵活的类加载机制，打破传统的双亲委派模型。

并发编程核心：Volatile、CAS 与原子类

Volatile 两大核心特性

1. 可见性

线程修改共享变量值后，其他线程能立即知道变更。volatile 修饰的变量写操作立即刷新到内存，读操作能看到最新值。

2. 禁止指令重排序

volatile 变量读写操作时插入内存屏障，禁止重排序。写操作不能与之前的读写操作重排序，读操作不能与之后的读写操作重排序。

典型应用：单例模式双重锁检查

利用 volatile 禁止”初始化对象”和”设置 singleton 指向内存空间”的重排序。

CAS 原理与 ABA 问题

CAS（Compare-And-Swap）即比较并交换，是实现无锁编程的原子操作。java.util.concurrent.atomic 包中的原子类都利用 CAS 保证复合操作原子性。

ABA 问题本质：共享变量初始值 A，线程 1 读取后准备执行 CAS，期间线程 2 将值修改为 B 后又改回 A。线程 1 执行 CAS 时会误判”值未被修改”，掩盖中间状态变化。

解决方案：AtomicStampedReference

引入版本号（stamp）概念，为每个值变化建立”时间轴”。每次更新操作不仅比较引用值，还会检查版本号是否匹配。即使引用值相同，只要版本号发生变化，CAS 操作就会失败。

乐观锁与悲观锁对比

类型 说明 适用场景
乐观锁（CAS） 不加锁，假设没有冲突，冲突失败则重试直到成功 适用于低冲突场景
悲观锁（synchronized） 线程获得锁后，其他需要锁的线程挂起 适合高冲突场景，确保强一致性

拒绝策略对比

1. AbortPolicy（默认策略）

直接抛出 RejectedExecutionException 异常，体现”快速失败”（Fail-Fast）原则。适用于需要严格控制任务提交的场景。

2. CallerRunsPolicy

调用执行自己的线程运行任务，采用”责任回退”机制，柔性降级。牺牲调用线程执行效率，换取任务不被丢弃。

3. DiscardPolicy

静默丢弃被拒绝的任务，简单高效，但可能导致部分任务丢失。

4. DiscardOldestPolicy

丢弃工作队列中最旧的任务，尝试重新提交新任务。保证最新任务得到处理，可能造成旧任务丢弃。

生产应用推荐：使用自定义拒绝策略，实现日志记录、告警、兜底处理。

Java 锁机制与 AQS 原理

Synchronized 锁状态演进

1. 偏向锁状态（01）

检测 MarkWord 是否为可偏向状态。线程 ID 为当前线程 ID 则执行代码块，否则通过 CAS 竞争锁。存在锁竞争时，升级为轻量级锁。

2. 轻量级锁状态（00）

虚拟机在线程栈帧中建立 LockRecord 空间。使用 CAS 尝试将 MarkWord 中 LockWord 字段改为指向当前线程 LockRecord 的指针。更新失败则自旋等待。

3. 重量级锁状态（10）

竞争加大时，线程等待时间长，自旋占用 CPU 时间，升级为 Monitor 锁。锁信息存储于对象 MarkWord 中。

AQS（AbstractQueuedSynchronizer）概述

AQS 是抽象的队列同步器，提供完整的同步编程框架。常用同步器如 ReentrantLock、CountDownLatch、ReadWriteLock 都基于 AQS 实现。

核心思想：如果共享资源空闲，将当前请求资源的线程设置为有效工作线程，资源设置为锁定状态；如果资源被占用，需要阻塞等待唤醒机制保证锁分配。

AQS 数据结构：

  • 同步状态 State：使用 Volatile 的 int 类型成员变量表示，通过 CAS 完成 State 值修改
  • Node 节点队列：线程被封装成节点，Node 为 CLH 变体队列中的节点

惊群效应与 AQS 解决方案：传统锁释放后同时唤醒所有等待线程，导致海量竞争。AQS 使用变种 CLH 队列，队列中线程只监视前面节点线程状态，线程唤醒只唤醒队头等待线程，有效解决惊群效应。

锁优化技术

1. 锁消除

JIT 编译器编译时通过逃逸分析，如果发现某个对象只能被当前线程访问，会将该对象的同步操作消除。

2. 锁粗化

JIT 编译器发现一系列连续操作都对同一个对象反复加锁和解锁，会将加锁范围扩展到整个操作序列外部。

3. 自适应自旋锁

JDK1.6 中，虚拟机在通知操作系统阻塞线程前加入自旋等待过程，避免频繁切入核心态，减少上下文切换开销。

Happens-Before 原则总结

Java 内存模型的核心规则，定义操作之间的可见性关系：

  1. 程序次序规则：一个线程内，按照代码顺序，书写在前面的操作先行发生于书写在后面的操作
  2. 管程锁定规则：一个 unLock 操作先行发生于后面对同一个锁 lock 操作
  3. Volatile 变量规则：对一个变量的写操作先行发生于后面对这个变量的读操作，禁止指令重排序
  4. 线程启动规则：Thread 对象的 start 方法先行发生于此线程的每个一个动作

IOC 容器启动流程

Spring IOC 容器的启动是框架的核心，入口是 AbstractApplicationContext.refresh()方法，定义了容器启动的 12 个关键步骤。

容器启动的五个阶段：

  1. 启动前准备阶段 - prepareRefresh()

Bean 生命周期四阶段

Bean 的生命周期包含四个主要阶段：实例化、属性赋值、初始化和销毁，完全由容器控制。

Bean 生命周期完整流程：

  • 实例化阶段：通过 createBeanInstance() 创建 Bean 实例，支持 Java 反射和 CGLIB 策略

循环依赖三级缓存机制

Spring 通过三级缓存机制巧妙地解决了循环依赖难题。当两个或多个 Bean 相互依赖形成闭环时，此机制确保正确注入。

三级缓存结构：

  1. singletonObjects（一级缓存）：存放完全初始化的 Bean 实例
  2. earlySingletonObjects（二级缓存）：存放提前暴露的 Bean 引用
  3. singletonFactories（三级缓存）：存放 ObjectFactory 对象，用于生产 Bean

当容器获取 Bean 实例时，getSingleton() 方法按”一级→二级→三级”顺序查询缓存。这种设计解决了循环依赖可能导致的死循环和 AOP 代理问题，符合 Spring”尽可能延迟代理对象生成”的原则。

AOP 动态代理实现

Spring AOP 通过动态代理技术实现切面编程，主要使用JDK 动态代理和CGLIB 动态代理两种方式。

JDK 动态代理：

  • 基于接口，使用 Proxy 和 InvocationHandler
  • 只能代理实现了接口的类
  • JDK 内置，无需额外依赖

CGLIB 动态代理：

  • 基于继承，通过继承目标类创建代理
  • 可代理没有实现接口的类
  • 基于 ASM 字节码操作，性能较高

在 Spring Boot 2.x 后，默认使用 CGLIB 作为动态代理实现，但可通过配置修改。ReflectiveMethodInvocation 类负责构建和执行代理链，通过责任链模式执行多个拦截器。

一、B+ 树索引原理与优化

MySQL InnoDB 存储引擎的核心索引数据结构

1.1 B+ 树核心特性

B+ 树是 MySQL InnoDB 存储引擎默认的索引数据结构，专为磁盘等外存设备设计，具有四大核心特性：

  1. 数据集中存储：所有数据记录仅存储在叶子节点，非叶子节点仅存储索引键（用于导航）
  2. 叶子节点链表：所有叶子节点通过双向链表连接，形成有序序列，支持高效范围查询
  3. 树高极低：通常 2-4 层，百万级数据仅需 3 次磁盘 I/O，确保查询稳定
  4. 平衡性：任何节点的子树高度差不超过 1，保证查询路径长度固定

1.2 B+ 树与 B 树对比

特性 B 树 B+ 树
数据存储 所有节点都可能存储数据 数据仅存储在叶子节点
范围查询 需要中序遍历，效率低 叶子节点链表直接遍历，效率高
查询稳定性 不同记录所需 IO 次数可能不同 所有记录 IO 次数相同
磁盘 I/O 优化 较好 更优，内部节点可存储更多键值

MySQL 选择 B+ 树的原因：

  • 内存占用：内部节点只存储索引信息，减少内存占用
  • 顺序访问：叶子节点通过链表相连，便于顺序访问和范围查询
  • 磁盘访问：节点大小等于数据块大小（16KB），最大化利用磁盘容量
  • 多级索引：支持多级索引，数据量增大时可不断分裂增加层数

1.4 索引优化策略

最左前缀原则

当查询条件包含复合索引的多个列时，MySQL 只能使用索引的最左前缀部分。

覆盖索引

查询的所有字段都包含在索引中，MySQL 可直接从索引中获取数据，无需回表查询。

优势：

  • 减少磁盘 I/O 操作
  • 避免随机 I/O（特别是对于包含大字段的表）
  • 可将查询耗时降低 50% 以上

索引下推（ICP）

MySQL 5.6+ 引入的优化技术，将 WHERE 条件中的过滤操作”下推”到存储引擎层执行。即使 status 不是最左前缀，ICP 允许存储引擎在索引中直接检查 status 条件，仅返回满足所有条件的行 ID。

三、事务 ACID 与 MVCC 并发控制

3.1 事务 ACID 特性

特性 含义 实现机制
A 原子性 事务中的操作要么全部成功，要么全部失败 Undo Log（回滚日志）
C 一致性 事务执行前后，数据库从一个一致性状态变换到另一个一致性状态 事务约束、外键约束
I 隔离性 多个事务并发执行时，一个事务的执行不应影响其他事务 锁机制、MVCC

MVCC 多版本并发控制

ReadView 生成时机：

  • RC（读已提交）：每次进行快照读的时候，都会产生新的 readview
  • RR（可重复读）：只有在第一次进行快照读的时候，才会产生 readview

读类型区分：

  • 快照读：读取的是数据库中历史版本的数据，不加锁（普通 SELECT）
  • 当前读：读取的是数据库中最新版本的数据，会对读取的数据加锁

四、锁机制与隔离级别

4.1 锁的分类

按粒度分：

  • 表锁：锁住整个表，粗粒度，并发度低
  • 行锁：锁住表中的一行，细粒度，并发度高
  • 页锁：锁住一页数据，中等粒度

按类型分：

  • 共享锁（S 锁）：允许事务读一行数据，S 锁与 S 锁兼容
  • 排他锁（X 锁）：允许事务更新或删除一行数据，X 锁与任何锁都不兼容

按模式分：

  • 记录锁（Record Lock）：锁直接加在索引记录上面
  • 间隙锁（Gap Lock）：锁定索引记录间隙
  • Next-Key Lock：行锁和间隙锁的组合

4.2 Next-Key Lock 防止幻读

定义：Next-Key Lock 是行锁（Record Lock）和间隙锁（Gap Lock）的结合。

作用：

  1. 锁住不仅是一个记录，还包括该记录之前的间隙
  2. 防止其他事务在这个范围内插入新数据
  3. 避免幻读

6.2 主从复制延迟问题

延迟原因：

  • 大事务：大事务在主库运行 30 分钟，从库也需要 30 分钟
  • 主从硬件配置不均衡：主库配置好，从库配置差

  1. 并行复制：

    • MySQL 5.6：基于库的并行复制
    • MySQL 5.7+：基于逻辑时钟的并行复制
    • MySQL 8.0+：基于 WRITESET 的并行复制（推荐）

  2. 优化从库配置：

    • sync_binlog 设置为 0，减少磁盘 I/O
    • innodb_flush_log_at_trx_commit 设置为 2
    • 禁用从库的 binlog

  3. 优化 SQL 执行：

    • 避免大事务：分批删除，分批更新
    • 使用合适的索引：避免全表扫描
    • 读写分离设计：一主多从，主写从读

四、分布式系统核心技术与中间件

构建分布式系统理论基础，详细阐述 CAP 理论、BASE 理论及分布式一致性算法。深入分析分布式事务解决方案。涵盖高频中间件技术：Redis 数据结构、持久化、集群模式及缓存一致性解决方案；消息队列的高可用、积压处理及顺序消费机制。

CAP 理论

CAP 理论指出一个分布式系统最多只能同时满足一致性 (Consistency)、可用性 (Availability)、分区容错性 (Partition Tolerance) 中的两项。网络分区是客观现实，因此实际选择是在网络分区时保证 C(一致性) 还是 A(可用性)。

  • CP 系统：优先保证一致性和分区容错性，牺牲可用性。适用于金融等强一致性场景。
  • AP 系统：优先保证可用性和分区容错性，牺牲一致性。适用于电商等高可用场景。

BASE 理论

BASE 理论是对 CAP 理论中一致性和可用性权衡的延伸，强调即使无法做到强一致性，系统也可以通过适当方式达到最终一致性。

核心三要素：

  1. 基本可用 (Basically Available)：允许损失部分可用性，如响应时间延长或功能降级
  2. 软状态 (Soft State)：允许数据存在中间状态，不影响系统整体可用性
  3. 最终一致性 (Eventual Consistency)：数据副本经过一段时间同步后最终达成一致

分布式一致性算法

Paxos 算法原理与实现

由 Leslie Lamport 提出，是第一个被证明完备的共识算法 (无恶意节点)。通过提议者 (Proposer)、接受者 (Acceptor)、学习者 (Learner) 三个角色，经过 Prepare 和 Accept 两阶段达成共识。

优点：简洁高效 (两轮消息)、保证线性一致性、具备容错性

缺点：难以理解和实现、不适用于动态系统、可能出现死循环

Raft 算法设计与应用

设计目标是易于理解和实现。通过明确的领导者 (Leader)、跟随者 (Follower)、候选者 (Candidate) 角色，以及 Leader 选举和日志复制机制保证一致性。

优点：易于理解和实现、明确的角色划分、适用于大多数场景

缺点：较高的网络开销、需要同步所有节点日志、不适用于高并发

Paxos 与 Raft 算法对比

特性 Paxos Raft
设计目标 理论完备性 易于理解和实现
角色复杂度 三个角色，可能混合 三个明确角色
领导者选举 无固定领导者 强制单一领导者
理解难度 非常困难 相对容易
适用场景 理论研究、高要求系统 大多数分布式系统

分布式事务解决方案

刚性事务：2PC (两阶段提交)

1. 准备阶段：协调者发送 Prepare 消息，参与者执行”预提交”操作，将结果返回给协调者。

2. 提交阶段：协调者根据结果决定发送 Commit 或 Rollback 消息。

特性分析：CP

优点：严格保障 ACID，对业务侵入小

缺点：同步阻塞，性能差，协调者单点问题

TCC (Try-Confirm-Cancel)

业务层实现的两阶段提交变种，包含 Try、Confirm、Cancel 三个阶段。以下单扣库存为例：Try 阶段占库存，Confirm 阶段实际扣款，Cancel 阶段回滚。

适用场景：需要强隔离性的分布式事务

Seata 分布式事务解决方案

提供 AT、TCC、SAGA 和 XA 事务模式的一站式分布式解决方案。包含 TC(协调者)、TM(管理器)、RM(资源管理器) 三个核心角色。

AT 模式：通过拦截 SQL 生成前后镜像实现无侵入事务

2PC 强一致性 低 差 金融等强一致性场景

消息顺序性

  • 防止故障扩散

Java 21 虚拟线程 (Virtual Threads)

核心原理：虚拟线程是 JDK 21 引入的轻量级线程实现，采用M:N 映射模型，大量虚拟线程复用少量操作系统线程。与传统平台线程的 1:1 映射不同，虚拟线程由 JVM 管理，内存占用仅几百字节，支持百万级并发。

实现机制：

  1. Mount/Unmount 机制：虚拟线程在需要 CPU 运算时挂载到载体线程，遇 I/O 阻塞时卸载，释放 OS 线程资源
  2. Continuation 技术：使用 Continuation 保存和恢复栈帧状态，实现线程状态的轻量级保存
  3. 避免 Pinning：使用 synchronized 或 native 方法会导致虚拟线程被”钉住”，应使用 ReentrantLock 替代

Kubernetes 核心架构

控制平面组件：

  • API Server：集群操作的唯一入口，提供 RESTful API 接口，处理认证、授权等机制
  • etcd：分布式键值存储数据库，存储集群所有配置与状态数据，采用 Raft 协议保证一致性
  • Controller Manager：运行控制循环，维护集群状态，包括 Node Controller、Deployment Controller 等
  • Scheduler：资源调度器，通过过滤、打分、绑定三阶段将 Pod 分配给合适节点

节点组件：

  • Kubelet：节点上的 Agent，管理 Pod 生命周期、健康检查、资源管理
  • Kube-Proxy：维护网络规则和流量转发，实现 Service 的负载均衡
  • 容器运行时：支持 Containerd、CRI-O 等符合 OCI 标准的运行时

核心概念与资源对象：

  • Pod：最小部署单元，一组容器的集合，共享网络和存储命名空间。Pause 容器作为根容器，使 Pod 内容器共享 IP 和存储
  • Service：服务抽象，提供稳定的网络访问接口，支持 ClusterIP、NodePort、LoadBalancer 等类型
  • Deployment：用于部署无状态应用，提供版本管理、滚动更新、副本管理功能

调度与资源管理：

  • 资源请求和限制：
    • requests：容器需要的最小资源
    • limits：容器可以使用的最大资源
  • 调度策略：亲和性调度、污点和容忍度、优先级和抢占

一、系统设计面试方法论

系统设计面试是衡量资深 Java 工程师架构能力的关键环节，涵盖需求分析、技术选型、架构设计、容量评估、扩展性思考五个核心维度。

1.1 系统设计四步法

  1. 需求澄清 (Clarify Requirements)：明确功能性/非功能性需求及约束条件
  2. 系统接口设计 (System Interface Design)：定义 API 接口与数据模型
  3. 高层架构设计 (High-Level Design)：绘制架构图，进行技术选型，明确数据流向
  4. 详细设计 (Detailed Design)：深入关键模块，进行容量规划与故障处理设计

1.2 常见面试评分维度

评分维度 考察重点 占比
需求分析 准确理解业务需求，识别核心挑战 15%
架构设计 系统分层、模块划分、技术选型合理性 25%
深入设计 关键问题解决方案（一致性、高可用） 30%
容量评估 QPS 预估、资源规划、扩展性设计 20%

2.2 三层架构设计与核心方案

客户端层：

  • 页面静态化：提前生成 HTML，减少服务端请求
  • CDN 加速：就近访问静态资源
  • 按钮控制：JS 控制秒杀开始时间，防止提前请求

接入层：

  • 负载均衡：Nginx/LVS 分发流量
  • 限流熔断：Redis/Guava RateLimiter 限制并发

业务层核心方案：

  • 两阶段异步下单：Redis 预扣库存 + MQ 异步写库
  • 库存预热：活动前加载库存至 Redis
  • 分布式锁：Redis SETNX+Lua 脚本保证扣减原子性

容量评估示例

商品 1000 件，参与用户 100 万，时长 10 分钟。峰值 QPS ≈ 667（二八定律），考虑峰值因子与 Buffer，系统需支撑~3200 QPS。Redis 单实例 QPS 约 8-10 万，足以支撑扣减。

三、海量数据 Feed 流系统设计

基于关系或推荐的动态流，核心在于推 (Push)、拉 (Pull) 模式的选择与结合。

3.2 核心传递模式与推拉结合方案

模式 优点 缺点 适用场景
推模式 (写扩散) 读性能好，实现简单，时效性高 写放大严重，存储浪费 粉丝少的普通用户
拉模式 (读扩散) 写逻辑简单，节约存储 读性能差，粉丝越多消耗越大 大 V 用户（粉丝多）
推拉结合 平衡读写性能，控制资源浪费 设计复杂度高 混合场景（如微博）

推拉结合实现要点：

  1. 用户分级：大 V(粉丝>10 万) 用拉模式，普通用户用推模式
  2. 发布流程：消息入 Kafka，查询粉丝列表，写入发件箱，按类型同步至粉丝收件箱
  3. 冷热分离：热粉丝（7 天活跃）推模式，冷粉丝（30 天未登录）拉模式
  4. 多级缓存：HBase(历史) + Redis(热点) + Caffeine(本地) 加速读取

四、系统容量评估方法论

从 10W 到 1000W QPS 绝非线性增长，提前预估最大 QPS 是架构师必备技能。

4.3 五步评估法

步骤一、二：分析日总 PV，评估平均 QPS

日均 PV 8000 万，一天活跃时间约 4 万秒，平均 QPS = 8000 万 / 4 万 = 2000

步骤三：评估高峰区间 QPS（二八定律）

峰值 QPS = (总 PV × 80%) / (每天秒数 × 20%)。示例：1200 万 PV 开屏广告，峰值 QPS ≈ 760

步骤四、五：压测单实例极限，规划资源

单机线上允许跑 QPS 的 80%。若峰值 QPS=7500，单机 QPS=1000，需 8 台，加 20% Buffer 共 10 台。

五、进阶设计与扩展思考

分布式事务选型

  • 强一致场景：银行转账用 TCC 或 2PC
  • 最终一致场景：订单 - 积分通知用本地消息表
  • 高并发场景：电商秒杀选 TCC
  • 长业务流程：旅游预订选 SAGA

99% 的调用不需要分布式事务，监控与快速修复成本更低。

高可用架构设计

  • 冗余设计：空间、时间、信息冗余
  • 容错策略：容错域、可恢复块、明确责任方
  • 可用性等级：
    • 核心服务：99.99% (全年 53 分钟)
    • 重要服务：99.95% (全年 260 分钟)

弹性伸缩策略

  • 横向扩展（水平）：加实例，成本效益高，适合无状态应用
  • 纵向扩展（垂直）：升单机配置，简单但成本高，适合有状态应用

六、面试实战技巧

答题框架

  1. 需求澄清：主动提问日活、QPS、约束条件
  2. 系统设计：先画高层架构图，再逐步深入
