5 年经验 Java 后端工程师·Java SE 核心知识深度指南

本指南专为 5 年经验的 Java 后端工程师设计，聚焦 Java SE 核心知识的深度理解。内容涵盖 JVM 底层原理、JUC 并发编程、集合框架源码、IO 模型及 Java 新特性，旨在帮助候选人建立完整的技术认知体系，应对高水平技术面试。

范围声明：严格限定于 Java SE，不涉及 Spring、MyBatis、MySQL、Redis 等框架或中间件。

第一章：JVM 深度剖析与调优

1.1 内存模型 (JMM)

1.1.1 主内存与工作内存交互模型

核心定义：JMM 定义了 Java 程序的内存访问规则，核心是主内存（Main Memory）与工作内存（Working Memory）的交互协议。

底层实现原理：

  • 主内存：所有线程共享，存储变量实例（堆内存）
  • 工作内存：每个线程私有，保存主内存变量的副本（CPU 缓存 + 寄存器）
  • 8 种原子操作：
    • lock/unlock：锁定/解锁主内存变量
    • read/load：读取主内存变量到工作内存
    • use/assign：使用工作内存变量/赋值给工作内存变量
    • store/write：存储工作内存变量到主内存

内存交互流程：

happens-before 原则（JLS 定义）：

  1. 程序次序规则：单线程内，前面的操作 happens-before 后面的操作
  2. 监视器锁规则：unlock 操作 happens-before 后续的 lock 操作
  3. volatile 变量规则：对 volatile 的写操作 happens-before 后续的读操作
  4. 传递性规则：A happens-before B, B happens-before C → A happens-before C

1.1.2 volatile 的硬件级实现

底层实现原理：

  • Lock 前缀指令：触发 CPU 缓存一致性协议（MESI）
  • 内存屏障：
    • LoadLoad：禁止读操作重排序
    • StoreStore：禁止写操作重排序
    • LoadStore：禁止读后写重排序
    • StoreLoad：禁止写后读重排序（最严格）

MESI 协议（缓存一致性协议）：

状态 含义 说明
Modified 已修改 缓存行已修改，与主内存不一致
Exclusive 独占 缓存行与主内存一致，仅当前 CPU 持有
Shared 共享 缓存行与主内存一致，多个 CPU 持有
Invalid 无效 缓存行失效

面试高频追问：

  1. volatile 能否保证原子性？不能，i++ 操作仍需 synchronized 或 AtomicInteger
  2. 64 位 long/double 的读写是否原子？非 volatile 情况下不原子，可能读到高 32 位是旧值
  3. volatile 的性能开销？写操作性能下降 10-15%（缓存一致性协议开销）

1.2 垃圾回收机制

1.2.1 G1 垃圾收集器核心算法

Region 划分机制：

  • 堆划分为多个 Region（默认 2048 个，大小 1M-32M）
  • Region 类型：
    • Eden：新对象分配区域
    • Survivor：Young GC 后存活对象复制区域
    • Old：老年代区域
    • Humongous：大对象区域（超过 Region 50%）

SATB（Snapshot-At-The-Beginning）算法：

  • 核心思想：在并发标记开始时，记录所有存活对象的快照
  • 实现方式：写屏障记录被修改的引用

Mixed GC 触发条件：

  • 堆占用率达到 InitiatingHeapOccupancyPercent（默认 45%）
  • 并发标记周期完成
  • 选择回收价值最高的 Region（Garbage First）

1.2.2 ZGC 核心算法

染色指针（Colored Pointers）：

  • 64 位指针中，使用高 16 位存储标记信息
  • 标记位：Finalizable、Remapped、Marked0、Marked1

读屏障（Load Barriers）：

  • 每次对象访问时触发
  • 检查指针标记，必要时进行对象移动

G1 vs CMS vs ZGC 对比：

特性 CMS G1 ZGC
算法 Mark-Sweep Mark-Compact Mark-Compact
停顿时间 不可预测 <200ms <10ms (Java 21: <1ms)
内存碎片 有 无 无
适用场景 低延迟 大堆（>6G） 超大堆（TB 级）
CPU 开销 低 中 高

面试高频追问：

  1. G1 的 Humongous 对象问题？超过 Region 50% 的对象直接分配在老年代，可能导致提前 Full GC
  2. ZGC 的适用场景？超低延迟场景（金融交易、实时计算），CPU 开销增加 10-15%
  3. 如何选择 GC？延迟敏感选 ZGC，大堆选 G1，兼容性好选 CMS

4.1 IO 模型对比

4.1.1 BIO/NIO/AIO 本质区别

同步 vs 异步：

  • 同步：应用进程等待 IO 完成
  • 异步：应用进程不等待，内核完成后通知

阻塞 vs 非阻塞：

  • 阻塞：IO 操作阻塞线程
  • 非阻塞：IO 操作立即返回

对比表格：

模型 同步/异步 阻塞/非阻塞 适用场景
BIO 同步 阻塞 连接数少且固定
NIO 同步 非阻塞 高并发、短连接
AIO 异步 非阻塞 高并发、长连接

5.3 GC 新进展

5.3.1 分代 ZGC 原理（Java 21）

核心改进：

  • 分代回收：新生代和老年代分开回收
  • 停顿时间：< 1ms
  • 吞吐量：损失<10%

性能对比：

GC 停顿时间 吞吐量 适用场景
G1 <200ms 高 大堆通用
ZGC (Java 17) <10ms 中 超低延迟
ZGC (Java 21) <1ms 中高 超低延迟 + 高吞吐

⚠️ 5 年经验必知陷阱：

  1. 虚拟线程的 ThreadLocal 泄漏：虚拟线程数量巨大，泄漏影响更大
  2. Record 的序列化：需要额外处理 serialVersionUID
  3. 模式匹配的向后兼容：需要 Java 21，老版本无法运行
  4. 分代 ZGC 的内存开销：分代管理增加内存开销
